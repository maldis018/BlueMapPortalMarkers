# BlueMapPortalMarkers — v0.3 Roadmap

Status: planning. Baseline is v0.2 (`0.2.0-SNAPSHOT`, commit `5229b94`), which has been
validated on a live Paper + BlueMap server. This document is a high-level roadmap for
v0.3 — it captures **scope, decisions, dependencies, and known risks** so a planning
agent can turn each item into a concrete plan later. It is intentionally *not* an
implementation plan.

Repo: https://github.com/maldis018/BlueMapPortalMarkers (public)

See `CLAUDE.md` for architecture, the threading model, and the load-bearing toolchain
constraints (`--release 25`, Gradle 9.4 pinned, `compileOnly` deps, no shading today).

---

## Item 1 — Admin commands: `/bmportals`

**Goal.** Give operators live control over the portal store and marker layer without
hand-editing `portals.json` or restarting. Primary motivating workflow: **WorldEdit and
most terrain tools don't fire `BlockBreakEvent`**, so portals removed/relocated that way
leave stale markers — operators need to rebuild the store from current reality on demand.

**Subcommands.**

| Subcommand | Behavior | Reuses (v0.2) |
|---|---|---|
| `reload` | Re-read `config.yml` and re-apply without restart. Config is read **only** at `onEnable` today, so re-pushing settings to the live `BlueMapBridge`/`PoiSweeper`/listener is the one genuinely new piece. Planner must decide what's safely hot-reloadable vs. what should warn "restart required". | — |
| `sweep [radius] [center]` | Force a POI sweep now; live-add new markers + `requestSave()`. See center resolution. | `PoiSweeper.sweep()`, `requestSave()` |
| `stats` | Report total + per-world portal counts (optionally last-sweep info). | `PortalStore.size()`, `inWorld()` |
| `purge [world]` | Remove stored portals (one world, or all), drop their markers, persist. Reuse the `synchronized` store mutators — don't touch the map directly. | `PortalStore.all()/inWorld()`, `bridge.removePortal()`, `requestSave()` |

**`sweep` center resolution.** The command resolves `center` into a `Location`, then calls
the existing `PoiSweeper.sweep(world, location, radius)` unchanged.

| `center` | Resolves to | World source | Sender requirement |
|---|---|---|---|
| *(omitted)* | default sweep: spawn + every online player | each world | any sender |
| `me` | sender's location | sender's world | **player only** |
| `<playerName>` | that player's location | that player's world | any sender |
| `x z` / `x y z` | those coords | sender's current world | **player only** |

- Console / RCON / command-block have no location → `me` and bare coords must error
  cleanly. Omitted form and `<playerName>` work from console.
- `radius` defaults to config `discovery.sweep-radius` when omitted.

**Decision — manual sweep is full-height.** `locateAllPoiInRange` searches a *sphere*, so a
`x z` center with a guessed Y could silently miss portals by altitude. The manual `sweep`
command should query **full world height** (like the chunk-load path already does), making Y
irrelevant for the coordinate case and removing the footgun.

**Cross-cutting.** Permission node (e.g. `bmportals.admin`, default `op`) gating all
subcommands, declared in `plugin.yml`; new `commands:` + `permissions:` blocks; a
`CommandExecutor` + `TabCompleter` (complete subcommands, world names, online player names).
Commands run on the main thread (safe for Bukkit + `PoiSweeper`); saves stay async.

**Out of scope.** Per-subcommand permission granularity; progress reporting/chunking for huge
sweep radii.

## Item 2 — Portal linking (Nether ↔ Overworld)

**Goal.** Help navigation by connecting a portal to its counterpart in the other dimension.

- Compute each portal's predicted counterpart via the vanilla **8:1 rule** (nether `(x,z)` ↔
  overworld `(8x, 8z)`), find the nearest **known** portal near that target in the other
  dimension within a tolerance, and put a **clickable deep-link in the marker popup** that
  navigates the BlueMap viewer to it (BlueMap encodes map id + position + zoom in the URL
  hash). The popup `detail` is already HTML (with escaping) in `BlueMapBridge.buildMarker()`,
  so an `<a href>` drops straight in.
- Even when no counterpart portal is known yet, show the **predicted destination coords** as
  text.

**Honesty constraints (must be reflected in UI wording).** Pairing is a *prediction*, not
ground truth — vanilla links to the nearest existing portal within a search box, or builds a
new one. Label it "predicted link", not a guarantee.

**Foundation fit.** `PortalStore` already keys by world + position; pairing is a coordinate
computation over the existing set. No new persisted state strictly required (can be derived),
though caching pairings is an option.

**Open question — blocking.** The exact **BlueMap deep-link URL hash format** must be verified
against the target BlueMap version (read BlueMap source/docs — do not trust memory; this is
how API specifics were confirmed for v0.1/v0.2). Capability is certain; precise syntax is not.

## Item 3 — Background sweeping  → **Deferred to v0.4**

**Goal.** Automatically catch portals far from spawn that no `ChunkLoadEvent` happened to
cover (e.g. a far base kept loaded by a chunk loader, outside the startup radius).

**Recommendation: defer the whole feature to v0.4.** Rationale:
- The scan call already exists (`PoiSweeper.sweep`), so a "framework-only in v0.3" split would
  ship scaffolding that can't be exercised — the substance and risk is the **performance
  budgeting** (spreading sweep work across ticks so a repeating task doesn't cause lag), and
  budgeting can't be validated without the scan actually running. Framework-without-scan is
  dead code.
- Item 1's admin `sweep` command already gives operators **on-demand** coverage, which
  downgrades background sweeping from a gap to a refinement.

**Captured design (for v0.4).** Repeating task on a config interval that sweeps around online
players (and/or iterates loaded regions), with a **per-tick query budget / work-spreading**
mechanism and a config flag to disable. Depends on Item 1's `sweep` plumbing (and ideally the
full-height query) landing first. Needs live performance testing — explicitly not shippable on
static checks alone.

## Item 4 — GitHub Actions release builds

**Goal.** CI that builds the jar on every push/PR and publishes a release artifact on tag.

**Scope.**
- Workflow: build + (once Item 6 lands) run tests on push/PR.
- On tag (e.g. `v0.3.0`): build and attach `BlueMapPortalMarkers-<version>.jar` to a GitHub
  Release.

**Decision — CI JDK.** The dev host needs JDK 26 only because that's what's installed; CI does
**not** have to replicate that. The build compiles `--release 25` and the pinned Gradle 9.4
runs fine on JDK 25. **Prefer JDK 25 (LTS, widely available in `actions/setup-java`/Temurin)**
to avoid depending on a JDK 26 distribution being available. (If JDK 26 is ever required,
verify a setup-java distribution provides it before relying on it.)

**Foundation fit.** Pure `./gradlew build`; no app code changes. `compileOnly` deps resolve
from Maven Central / PaperMC / BlueMap repos already configured in `build.gradle.kts`.

## Item 5 — bStats metrics + update checker

**Goal.** Anonymous usage metrics (bStats) and a console notice when a newer release exists.

**Decision — bStats forces introducing shading.** The bStats `Metrics` class must be **shaded
and relocated** (`org.bstats` → an internal package) into the plugin jar. The project currently
shades nothing (`CLAUDE.md` notes deps are `compileOnly`, never bundled), so this introduces
the Gradle Shadow plugin + a relocation rule — a real build-philosophy change the planner
should call out. If shading is unwanted, ship the update checker alone (no shading needed).

**bStats implementation** The application is registered with bStats as Plugin ID `31718`. 

**bStats Gradle configuration.** If shading is accepted, integrate via:

```gradle
repositories {
    mavenCentral()
    // your other repositories
}

dependencies {
    implementation("org.bstats:bstats-bukkit:3.2.1")
    // your other dependencies
}

plugins {
    id("com.gradle.up.shadow") version "9.3.1"
    // your other plugins
}

tasks.shadowJar {
    configurations = project.configurations.runtimeClasspath.map { setOf(it) }

    dependencies {
        // Only merge bStats into the final jar, no other dependencies
        exclude { it.moduleGroup ≠ "org.bstats" }
    }

    // Relocate bStats into the plugin's package to avoid conflicts with other
    // plugins using bStats
    relocate("org.bstats", project.group.toString())
}
```

Build with `./gradlew shadowJar` to produce the shaded jar with bStats included.

**Instantiate metrics** Instantiate the Metrics class in your plugin's onEnable() method.
```java
import org.bukkit.plugin.java.JavaPlugin;

public class ExamplePlugin extends JavaPlugin {

    @Override
    public void onEnable() {
        // You can find the plugin id of your plugins on
        // the page https://bstats.org/what-is-my-plugin-id
        int pluginId = 31718;
        Metrics metrics = new Metrics(this, pluginId);

        // Optional: Add custom charts
        metrics.addCustomChart(
            new SimplePie("chart_id", () -> "My value")
        );
    }

}
```

**Update checker.** Poll the GitHub Releases API for `maldis018/BlueMapPortalMarkers`, compare
to the running version, log a single INFO line on enable if newer. Off the main thread; fail
silent on network error. Add a config toggle. **Depends on Item 4** (releases must exist to
check against).

## Item 6 — Real JUnit test suite

**Goal.** Replace the jshell-only verification with an actual automated suite; do this
*alongside* whatever ships so coverage doesn't lag the growing surface area.

**Scope.**
- JUnit 5; new `test` source set + `testImplementation` deps.
- **Gotcha:** `PortalStore` uses gson, which is currently `compileOnly` (provided by the server
  at runtime). Tests of `load`/`save`/migration need gson on the **test** classpath →
  add `testImplementation("com.google.code.gson:gson:…")`.
- High-value, easily unit-tested pure classes: `Portal` (`contains`/`overlaps`/`markerId`/
  `equals`), `PortalClustering` (flood-fill grouping + bounds), `PortalStore` (overlap dedup,
  `removeContaining`, v0.1→v0.2 JSON migration round-trip — formalize the existing jshell check).
- Bukkit/BlueMap-touching classes (`PortalListener`, `BlueMapBridge`, `PoiSweeper`, plugin entry)
  are hard to unit-test without MockBukkit — list MockBukkit as optional/stretch, don't block on it.
- CI (Item 4) should run the suite.

## Suggested sequencing

Dependencies between items:

1. **Item 6 (tests)** and **Item 1 (admin commands)** — independent, start anytime; tests first
   gives CI something to run.
2. **Item 4 (CI)** — independent; benefits from Item 6 existing (so CI runs tests).
3. **Item 2 (portal linking)** — independent, but **blocked on verifying the BlueMap deep-link
   URL format** first.
4. **Item 5 (bStats + update checker)** — **depends on Item 4** (releases to check against);
   bStats portion gated on the shading decision.
5. **Item 3 (background sweeping)** — **deferred to v0.4**; depends on Item 1's sweep plumbing.

## Open questions for the planner
- Background sweeping: accept the v0.4 deferral, or force it into v0.3? (recommendation: defer)
- bStats: accept introducing shading, or ship the update checker alone?
- `reload`: which settings are hot-reloadable vs. "restart required"?
- BlueMap deep-link URL hash syntax — verify before planning Item 2.
